# v0.16 / #50：方向校正与长程自治的独立架构审查

日期：2026-10-05。性质：non-normative research；不是生产规则、发布决定或实际 `/goal` 验证。

本次问题是：如何让 Agent 自主执行更久，同时尽早发现“不该继续做这件事”。2026-09-27 的两份审查仅属历史背景，不作为本次结论的任务框架。

**结论：保留完整任务自治，收紧的是未经验证的投入承诺，而不是执行步骤数量。Browser 负责方向论证与重新评估；执行 owner 负责局部适应、识别反证并停止失效路径；用户保留重大价值和授权决定。`/goal` 是这一安排的宿主执行选项，不是方向正确性的来源。**

## 1. 有 Run-to-Gate，为何仍然中继很多？

Run-to-Gate 规定一个已授权任务内部应怎样推进；它本身不保证任务划分合理、规则已在实际宿主加载、宿主持续运行或两端能直接读取同一事实。至少需要区别以下现象：

| 现场现象 | 可能原因 | 对应处理 |
| --- | --- | --- |
| 每张工单都完整执行，但用户仍不断复制下一张 | 工单完成点过早，或把同一结果切成过多阶段 | 扩大到一个可独立验收的结果；删掉没有真实决策作用的边界 |
| 目标和权限清楚，做完局部步骤就说“可以继续” | 普通交互模式、指令未加载、或模型过早收尾 | 核实部署与实际停止原因，再试原生持续模式 |
| 每次都遇到真实授权、人类专属调用或价值取舍 | 任务跨越真实信任边界 | 在现有授权允许时提前备齐条件；其余保留，不能让 `/goal` 绕过 |
| IDE 自己能继续，却等人传日志或仓库状态 | 信息仍分散在会话，缺少可直接访问的事实来源 | 就近读取 canonical artifact；只搬运另一端确实读不到的差量 |
| 新证据改变了原任务是否值得做 | 正当的方向校正 | 用证据重评；这是必要中断，不能当作自治失败 |

v0.16 已反对微工单，但同时保留阶段拥有权、Browser 派发以及最终 Browser Review。它们不逻辑矛盾，却可能在实际使用中被解释成“每过一个认知阶段都交回 Browser”。单靠把 Run-to-Gate 再写强一次，不能消除这种使用模式。

我的诊断优先级：先看真正的停点和工单完成条件，再看宿主模式。若工单只要求“分析并返回方案”，`/goal` 完成方案后停止完全正确；它不会自动获得实施授权。若工单已含实现和验证，仍需要用户说“继续”，宿主持续模式才是直接候选。

## 2. Ownership：不宜把方向判断与执行判断绝对分给两个宿主

“Browser 控方向、IDE 控执行距离”可以表达愿望，但作为责任边界不够准确：

- 方向不是由 Browser 单方面拥有的事实。用户拥有价值取舍；Browser 应对“为什么值得做、哪些前提支持这个选择”负责；IDE 可能最先发现前提不成立。
- 执行距离包含成本、外部影响和不可逆承诺，不能完全归 IDE 自定。IDE 应自由决定边界内的步骤、并行、局部实验、重试和实现路线。
- 执行 owner 必须有质疑、拒绝继续失效路径的职责，不能只把反证归类成“需要继续修复的错误”。Browser 也不能将自己早先的建议视为不可反驳的权威。

更准确的划分：**用户决定重大取舍与授权；方向负责人维护当前目标及其理由；执行负责人在约束内自主推进并检验关键前提；验证者检查结果和声称是否相符。角色可以按事实位置落在不同宿主，不需要始终是一对固定会话。**

Browser 的正常介入点应是：开始时校正问题，遇到使原选择失效的证据时重新评估，以及在结果形成后做独立接受判断。它不需要为每一次工程路线改变盖章。

执行距离不是预先分配的步数。更好的问题是：下一次值得外部判断的证据什么时候出现？在此之前允许承受多少可撤销投入？

## 3. `/goal` 的地位

Google 当前官方文档明确将 `/goal` 描述为持续工作直到目标实现，可自主 build、diagnose、correct，不逐轮请求确认；页面列明 Antigravity 2.0 与 CLI 支持。[官方 Slash Commands](https://antigravity.google/docs/slash-commands/)。CLI v1.0.14（2026-06-30）变更记录写明移除 goal 最大运行限制，可运行到完成或取消。[官方 Changelog](https://antigravity.google/docs/changelog)。

这些事实支持其作为“让已定义的执行闭环持续运行”的实现。它们不证明当前用户安装版本已正确启用，不证明能识别业务方向错误，也不证明项目要求的所有门禁、预算、取消和上下文恢复行为已经得到验证。

判断分三层：

1. **任务契约清楚、无必要外部决策、却因回合结束频繁停下：** `/goal` 可能是关键运行缺口，值得优先试用。
2. **任务过碎、授权尚缺、事实跨端不可达：** `/goal` 只带来局部收益，主要原因仍在任务边界与协作方式。
3. **任务目标或承重前提错误：** 用 `/goal` 增加坚持程度是在错误层次优化；它可能更高效地扩大损失。

应把 `/goal` 的目标设为“完成授权范围内的可审查成果，或在前提失效/边界触发时携证据返回”，不应设为“无论如何把项目做完”。这是建议的任务语义，不是已验证的 Antigravity 保证。若宿主在真实暂停条件下仍强制续跑，该类任务就不适合用它。

## 4. 哪些任务可以长程执行？

判断依据是目标稳定性、反馈可信度、可逆性和影响范围，而非任务总时长或“探索/实现”标签。

| 情境 | 合理执行方式 | 什么证据要求改变方向 |
| --- | --- | --- |
| 已确认接口下的迁移、行为明确的 bug 修复，局部反馈可靠 | 一次执行到完整候选和验证结果 | 必须破坏已接受兼容性或扩大权限才能继续 |
| 成因未知的复杂 debugging，目标行为清楚 | 可以长程调查、试验和换假设；不必每个假设交回 Browser | 原问题不存在、目标行为冲突，或修复要求业务取舍 |
| #50 这样的研究，输出是有依据的判断 | 在明确资源与停止范围内自主查证，允许否定原候选 | 已无新的决策相关证据，或需要真正外部实验才可继续 |
| 想靠引入 `/goal` 解决全部中继，但尚不知实际停止原因 | 先做一次窄诊断，不先开发通用适配层 | 停点主要是授权/工单边界，而非回合终止 |
| 重写架构、替换工作流，价值与约束还在争议 | 先校正问题、核实承重前提；可委托有界探索 | 不同方案涉及用户价值、重大成本或不可逆承诺 |
| 发布、生产迁移、外部写入 | 准备和验证可以长程；承诺动作按真实授权边界处理 | 缺授权、回滚条件不成立或影响范围扩大 |

“先校正方向”不等于强制先开一轮 Browser 讨论。能由执行端通过廉价事实检查解决的疑问，就地解决；只有改变价值选择、承诺或授权的部分才上行。

## 5. 最小机制：前提可被推翻，损失有上限

已有 Mission Contract 包含 Goal / Scope / Acceptance / Gate，不需要新 registry 或复杂状态机。对确有走错方向风险的任务，在现有契约中补清以下信息即可；若已有内容覆盖，不重复写：

1. **希望改变的实际结果，与尚待核实的关键前提。** 不把“采用某方案”偷换成用户结果。只列会改变是否继续的前提，不穷举所有不确定性。
2. **可承受投入与不可跨越的承诺。** 可以是一个隔离候选、一次有界实验或实际资源上限；不用统一时间阈值。外部副作用不能仅靠“以后 review”兜底。
3. **何种证据使当前路径失效。** 如需求相互冲突、数据不支持预期收益、必须降低验收标准才可通过、成本/范围越界、重复尝试不再增加信息。

执行期间遵守一条反馈规则：**普通实现失败就地修复；反证推翻承重前提时，停止依赖该前提的工作并返回最小反证。** 若契约已允许多个实现路线，IDE 可直接换路。无关且仍获授权的工作可以继续，避免局部问题冻结整个任务。

如果关键假设只在大规模实现后才得到检验，应在依赖它的投入之前选择最便宜、能改变决定的验证；若没有廉价可靠验证，就缩小投入承诺，接受仍有未知。不是所有任务都必须新增 probe 阶段。

成果接受需有执行者不能随意改写的依据：用户行为约束、外部接口、固定的验收条件或必要的独立验证。不能以“自己改了测试然后测试全绿”证明方向正确；验收需要修改时说明依据与影响。固定 SHA 保证审的是同一制品，不保证做的是值得做的事。

没有通信自动化也能先实施：任务中保留足够前提信息，IDE 本地就能触发停止，然后只需一次语义中继。异步 Browser 发现重大反证时，应通过实际可用的中断/取消路径撤回受影响授权；不能假设一条未送达的消息已经停止运行。

提示词中的预算和停止条件只是行为约束。若潜在损失不能接受，应使用宿主实际支持的预算、权限或隔离限制；没有这些能力时缩小任务暴露。不能把“模型应该停”写成硬保障。

## 6. 从第一性原理重新设计

我会默认从**一个能接近主要事实并执行验证的工作 owner**开始，而不是默认配置 Browser Lead + IDE 两个长期会话。软件工作通常应靠近代码和运行时；以外部研究为主的工作则可靠近资料。

用户给这个 owner 结果、约束和重大决策边界。owner 自主获取事实、调用工具、委托调查并迭代。复杂的方向选择按需找独立 challenger，重大成果按风险找独立 verifier。上下文记录在已有 Issue/Spec/制品中，避免两个会话分别维护一份当前计划。

需要保留的是两种反馈：局部执行快速自校正，以及新证据对原目标/前提的重新审视。两种反馈不必对应两个应用；独立判断也不要求常驻另一端或更高级的指挥者。

只有 Browser 持续拥有 IDE 无法经济获得的外部上下文、跨项目协调或独立审查价值时，才维持长期 Browser 角色。其收益应抵得过上下文损失、等待和人工搬运成本。这里给的是从零设计的判断，不是已经证明迁移优于当前架构，更不是本次授权的生产重构。

## #50 的 Anthropic 依据能支持到哪里

W2S 原文报告了便宜验证关键假设、利用训练日志区分实现失败与方法失败的开发观察，同时明确这些观察尚未充分验证。[W2S 原文](https://alignment.anthropic.com/2026/automated-w2s-researcher/)。公开 prompt 仍有 high-level workflow，并允许迭代和换方向，不能将其解释为取消所有流程。[固定版本 prompt](https://github.com/safety-research/automated-w2s-research/blob/79a0562fa1a2c246048ed7c009f3684907987b05/w2s_research/research_loop/prompt.jinja2)。

后续研究使用独立 evaluator、冻结研究说明、针对实际代码的 monitor 等约束；这说明自主探索与完整性边界能够并存，并非越少门禁越好。[后续完整报告](https://alignment.anthropic.com/2026/automated-alignment-researchers/)。其官方摘要也列出研究失败模式、能力检查和代理评估等局限。[官方摘要](https://www.anthropic.com/research/automated-researchers-mitigate-alignment-failures)。

本审查借鉴的是“反馈与失效前提应改变执行”的机制。这些研究没有比较 Matt、Browser/IDE 分工或 `/goal`，不能拿它们替代本地适用性证据。

## 最小下一步与可推翻条件

总体判定：**MINIMAL CLARIFICATION；`/goal` 的本地适用性为 EXPERIMENT REQUIRED。** 不再增加一轮抽象的“自治原则强化”，也不先建运行平台。

以下均为待决建议，不属于本次持久化 Work Unit。下一 Gate 是 Browser fixed-ref review；真实 stop-cause trace 与一次 bounded `/goal` pilot 由 #50 后续单独决定。

- 对一个最近真实的 v0.16 任务，查看每次停止时任务是否完成、是否有新决策/授权、是否只是等待“继续”。这可直接区分工单边界、宿主持久性与必要中断。
- 对一件本来就要做、目标已清楚且可逆的工作，在实际 Antigravity 宿主确认命令与权限后使用 `/goal`。观察是否到达原完成点、是否仍要人传普通状态、真实停止条件是否有效、结果是否符合原验收；不为统计对称强制重复同一任务。
- 若停止集中在普通回合结束且原生模式确实解决，可在宿主使用说明加入条件化建议。若停止集中在真实信任边界，则接受它们；若集中在过碎工单或信息搬运，调整对应边界或事实访问。若出现忽略反证、越界或不能停止，拒绝把该模式用于相应风险等级。

成功标准是“更少的无价值介入，同时及时停下失效路径”，而非运行更久、报告更少或单纯任务完成率更高。本次没有执行上述试用，不能声称已证明效果。

## 沉淀范围

语义分类：发布/文档核实为 Fact；架构建议为待验证 Pattern / Decision candidate。五问过滤：本次为特定 frontier 的判断；普适性仍待现场证据；受众为维护者；已有 Spec/Playbook 拥有规范性规则；本文件不创建第二 SSOT。减法优先：将无决策价值的阶段交接与重复规范删减，优先在现有契约补清失效条件，不新建通用框架。
