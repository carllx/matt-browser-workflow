# 当前方向独立审查：先验证减法，再扩展工作流

日期：2026-09-27。状态：非规范性审查建议，未批准的实验与架构候选。

## 结论

项目解决的真实问题值得解决：分离的上下文与执行环境之间，如何让任务不失真地完成。但当前体系正在把这个问题扩张为通用 Agent 行为治理。我的建议是暂停给下一版增加 placement gate、learning check 与 global-rules 分类机制，先比较当前体系和一个显著更小的执行契约。

最有希望的替代方案是：一个 Work Unit 一个负责到底的 Agent；User 决定目标和重大取舍；工程反馈密集的工作通常由 IDE 主持；Browser 按需要提供产品推理、外部研究或独立审查。跨端时共享目标、已接受决定、产物引用和验收证据。宿主行为交给宿主配置，工程事实交给测试与邻近文档，发布完整性交给发布工具。

这是值得验证的方向，不是已经证明优于 v0.15 的结论。不要直接大改生产规则，也不要用一次“减法重构”替代本应做的小实验。

## 1. 重新定义问题

真正需要优化的是：**在目标、权限与验收不失真的前提下，一次工程任务需要多少人类注意力、交接、等待和返工。**

Browser/IDE 物理分离是现实条件，不应该自动变成永久的组织架构。Browser 长期拥有最多产品讨论是状态；它应永远担任 Workflow Steward 是设计选择。IDE 拥有工作目录也不代表它不能做需求澄清、研究、读取 tracker 或主持决策准备。

区分下面几类问题，目的在于把干预放对位置，而不是再建立一套术语体系：

| 问题 | 首选承担者 | 工作流真正需要保留的部分 |
| --- | --- | --- |
| 用户目标、范围、重大取舍 | User + 当前负责 Agent | 清楚的授权及升级边界 |
| 工程事实与已知正确行为 | 代码、测试、接口文档、项目 Issue | 交接时能找到验收输入 |
| rules/skills/plugins/hooks 的加载和优先级 | Harness 配置与诊断 | 关键能力无法满足时显式报阻塞 |
| 权限、机密、破坏性操作 | 工具权限、OS、CI/发布设置 | 不声称 prompt 等价于强制保障 |
| 模型漏读、误判、啰嗦 | 小规模行为评测、输入与工具反馈改进 | 不把每次失败直接升格为永久规则 |
| 跨环境结果差异 | 最小环境记录与针对性重放 | 记录足以解释关键差异的条件 |

Global rules 主要属于执行环境的输入来源及 Harness 指令加载问题。它们可能包含用户偏好、组织政策或工程约束，不能单凭“位于 home”判断其合法性或重要程度。

## 2. 按重要性排序的发现

### 2.1 额外工作流的净价值尚未得到充分证明

现有体系很擅长说明“怎样才符合规范”，但对“比更简单的方式多带来多少可靠性”证据不足。

具体证据不是“文档看起来长”：

- [范围保真探针](../evals/scope-fidelity-probe-2026-09-11.md) 的基线和候选均通过三个场景，原记录明确说没有证明相对提升。
- [有限前瞻验证](../evals/bounded-strategy-adjudication-2026-09-11.md) 使用非 fresh、非盲化的代理；初次有 PARTIAL，复核同时澄清输入并提供反馈。能支持边界措辞修正，不能隔离出新增规则的因果收益。
- [#33 smoke](https://github.com/carllx/matt-browser-workflow/issues/33#issuecomment-5496575648) 确实存在，不能说项目从未做 runtime 验证。但评论中的模拟 IDE evidence、规划输出与 R4 替换 fixture，不足以证明真实工程任务总耗时、返工或人工注意力下降。
- [#32 最新讨论](https://github.com/carllx/matt-browser-workflow/issues/32) 已记录 runtime efficiency UNVERIFIED、cost feedback NEGATIVE、NO PRODUCTION CHANGE WARRANTED。这是既有调查结论，不是我新测出的成本。

下一次修改的举证责任应包括：相比保留现状或删除一段机制，它改善了什么。兼容 Matt、文案清楚、静态审查 PASS 都不能单独回答这个问题。

### 2.2 具体强制义务与抽象效率原则存在结构性张力

v0.15 的启动入口要求读取 Spec/Playbook、核实发布身份、同步现场、Matt 漂移感知、定位、setup 检查、placement、会话目标建议等；这些有按需条件，并非每个问题都执行。但对规划、Review、派发这类常见工作，多个条件会同时触发。[启动入口](https://github.com/carllx/matt-browser-workflow/blob/v0.15/chatgpt-project/project-instructions.md)

随后再要求“最轻充分、充分即止”，并不能消除前述义务。Agent 做更多确认，有时是对现行契约的合理执行，而不只是模型的效率缺陷。

本地测量三核心文件共 982 行、96,942 bytes；Playbook 596 行但 50,604 bytes。这个数字只能说明行数不能代表读取负担；它既不证明 attention overload，也不意味着这些 ChatGPT Sources 受 Antigravity Rules 的文件限额约束。需测的是实际加载、阅读与行动成本。

### 2.3 发布完整性已经侵入实验内环

[现有 eval 协议](../evals/behavioral-regression-evals.md) 为解决候选无法通过启动 Fail-Closed 的问题，引入 H/S/T、identity-only overlay commit、immutable prerelease、隔离测试 Project。

隔离生产与测试是必要的；每次候选 prompt 实验必须先成为已发布版本，并不是逻辑必需。这是当前架构让“允许测试”依赖“已经发布”的直接例子。

未来可允许显式测试模式加载固定候选 SHA 与文件摘要，禁止该结果被标成生产接受或部署。正式发布仍冻结 tag。实验的可追溯性与发布资格应分开。当前 v0.15 门禁不被本建议豁免；在改变协议前，只做离线/隔离研究比较，不能冒充正式部署验证。

### 2.4 证据来源分类有价值，但不能替代证明范围

Browser 读到固定 SHA 的代码，能证明“审的是哪些代码”；不能证明这些代码在某台 Mac 上成功执行。Browser 读到 IDE 报告，可以核实“报告存在”，不能自动证明报告内每项执行事实。不同角色重复阅读同一二手摘要，也不构成独立证据。

保留来源纪律，但每个关键结论应说明具体对象与限制，例如“直接读取此 SHA；本地测试由 IDE 报告；CI 未覆盖 GUI”。无需每个普通句子贴标签。

Antigravity 纠错案例支持一手来源复核的价值；没有对照证据证明必须由 Browser 做，或者所有任务都需要双 Review。最靠近官方资料的 IDE、独立 reviewer 或 Browser 均可能完成该核查。

### 2.5 #43 的根因尚未从合理解释升级为因果证据

[#43](https://github.com/carllx/matt-browser-workflow/issues/43) 从“出现错误派发”推到“retrieval seam 缺强 pointer”。原文援引的方法论解释了为什么 pointer 可能有效，但没有排除角色默认、缺少 Browser 执行能力、上下文压缩、模型变异等原因。

“Skill selected + Placement resolved”仍让同一个 Agent 自评自己是否正确完成。它可能帮助提醒，也可能只是多了一句合理化陈述。

更简单的候选：**已有负责人默认继续，只有实际工具/反馈需求或职责冲突才交接。** 将复杂 placement 判断用于需要换端的例外，而不是每选一个 Skill 都重新求解。Browser 已持有产品讨论时继续主持；IDE 正在调试时也不必为了阶段名回到 Browser。

这会减少路由次数，仍需与 pointer 修补方案比较，不能预先宣布更好。

### 2.6 #44 两个案例不足以证明需要通用完成门禁

[#44](https://github.com/carllx/matt-browser-workflow/issues/44) 的方向中，最有用的是把行为留在工程环境里。最值得拒绝的是未经比较就把每个 Work Unit 结束前的 learning check 变成义务。

stdin EOF 应优先由进程适配层的集成测试保护：启动可控子进程，验证输入关闭后能退出、捕获结果并处理超时；移除 EOF 行为应使测试失败。不能只断言两个属性被赋值，也不能只写 ADR。

Stop Hook 的 payload 是接口能力证据；它不独自证明 exact routing 的完整可靠性。还需检验 conversation ID 在目标场景的稳定性、并发会话、缺失字段、重复/迟到事件等真正影响方案的条件。把去敏 fixture、最小运行探针和接口说明放在适配器附近，比新 Workflow invariant 更直接。

“曾经成功”不等于永久正确。记录版本与适用条件，允许新证据推翻旧方案，避免 Known-Good 变成历史实现冻结。

## 3. Authority 与 global rules：改变模型的用途

三层模型可保留为“哪类材料拥有哪类定义”的导航，但不应被理解为 Harness 实际执行的指令优先级，也不该被当成完整事实可信度模型。

需要分开回答三个普通问题：

1. 谁有权批准目标、约束或变更？
2. 某事实的证据是什么，适用于哪个版本和场景？
3. 本次执行实际上受哪些输入、工具权限和环境配置影响？

一个全局个人偏好主要属于第 3 项；组织强制政策也可能属于第 1 项；测试日志属于第 2 项。文件位置不能决定全部答案。因此既不需要机械加“第四层”，也不应坚持“最多只能三层”。建议删去反复出现的“不构成第四权威”防御性表达，改用来源、权限和适用范围的普通描述。

### 官方核查的实质结果

[Rules](https://antigravity.google/docs/rules/) 明确各 scope 累加，直接冲突时具体目录规则优先；超过单文件 24,000 bytes 会截断，active global/always_on 共享 20,000-token 预算，超额大文件降为 pointer。由此不能推导项目规则可排除全局影响，也不能仅凭文件存在证明全文已激活。

[/plan](https://antigravity.google/docs/plan/) 是结构化探索与计划入口；[Artifact Review](https://antigravity.google/docs/artifact-review/) 仍明确区分 Planning/Fast，且 Request Review 与 Always Proceed 决定是否暂停。计划流程不等于工具权限强制。

[Hooks](https://antigravity.google/docs/hooks?tab=ide) 覆盖 PreToolUse、PostToolUse、PreInvocation、PostInvocation、Stop，可用于事件观察及部分工具控制。这不证明某个本机旧插件已经正确配置，也不证明能移除已加载 global prompt。

[Workflows](https://antigravity.google/docs/ide/workflows/) 与[迁移文档](https://antigravity.google/docs/migration/workflows-to-skills/) 明确 2026-11-01 退休。它们描述 Antigravity 产品的 Workflows 文件机制，不能仅凭同名认定本项目 Browser Workflow 必须迁移。

[Terminal sandbox](https://antigravity.google/docs/sandbox?tab=cli) 约束 shell 的 OS 访问，不证明宿主进程不会读取个人规则。本次没有找到官方保证的“关闭所有 global rules”或完全隔离配置的 native profile 开关；这是未找到证据，不是证明功能不存在。

### 对 A–F 候选的明确裁决

| 候选 | 判断 |
| --- | --- |
| A：项目规则覆盖即可，完全不用管 | 不成立为普遍保证；对低风险日常工作可能已足够，无需例行扫描 |
| B：改为追求环境可复现性 | 部分成立；先追求关键结果和边界稳定，不追求逐字/逐步轨迹一致 |
| C：隔离 global | 适合受控评测、无人值守或高后果任务；先验证隔离能力与维护成本 |
| D：第四 Authority | 不建议；先拆开定义归属、证据与实际指令来源这三个问题 |
| E：Harness precondition | 比新增治理层简单；首次或配置变化后检查与任务有关的前提，不保证永久有效 |
| F：复用 Dynamic Capability Verification | 对日常兼容性诊断基本足够；它不能充当环境隔离或无冲突证明 |

“只有 material 才 probe”还有循环判断：未知规则的影响，怎么先判定 material？应由任务需要的保证和可观察异常触发，而不是先承诺自己知道没有影响。例如任务要求无人值守而实际 policy 会暂停，或某 global hook 会自动继续应停的流程，就值得核实。

不新增 NON-MATERIAL/MATERIAL/BLOCKING 状态体系；已有“可继续 / 缺少条件 / 无法满足门禁”足以表达处置。Probe 问题也应具体：本任务需要什么权限/行为，哪些已知配置可能妨碍它，有什么运行证据。让 Agent 回忆“所有 active rules”不能作为完整性证明。

## 4. 更简单的替代架构与可靠性目标

### 首选候选：一个负责人，按需咨询

每个 Work Unit 只有一个对交付负责的 Agent。它接受四件事：目标与非目标、关键输入、可执行权限及需人类决定的边界、完成证据。已有 Issue 包含的内容只传指针和差量。

对多数实现/调试工作，IDE 同时主持工程推理、实验、修改和验证。Browser 在有真实增量价值时承担产品澄清、外部研究、跨项目判断或独立审查。产品探索已发生在 Browser 时，先在那里完成必要澄清再交接，不把既有深度讨论机械搬走。

另一个值得保留的对照是原生 IDE + 项目约束，完全没有常驻 Browser Steward。Antigravity 已有规划与审阅机制，因此额外层需要证明增量价值；原生能力存在本身也不证明质量更高。

Review 的独立性来自独立证据、不同失效视角和检查内容，不来自一个叫 Browser、另一个叫 IDE。低风险变化可以一次适当的 review；高风险、复杂验收或利益冲突时增加独立检查。当前明确 mandatory 的 gate 继续执行，未来修改后才改变默认。

### 可复现性应按后果分级

| 场景 | 足够的目标 | 建议方式 |
| --- | --- | --- |
| 日常可逆开发 | 验收、授权与关键行为稳定；允许计划/措辞不同 | 项目规则、测试、必要时窄 probe |
| 行为评测或跨 host 故障 | 能解释输入差异并重放关键失败 | 记录相关模型/产品版本、规则与技能版本、工具权限；受控配置比较 |
| 无人值守或高后果操作 | 未授权动作被执行层阻止，候选与验证绑定 | 受管环境、最小权限、CI/发布控制；个人规则不自由注入该执行环境 |

即使配置完全相同，也不能承诺模型轨迹确定性。目标是可审计的输入、足够稳定的结果以及明确的失败处理。

Clean-room 只在它能回答实际问题时有价值。独立 OS 账户/专用机器比 worktree 更接近隔离用户目录，但仍须核查同步、插件和实际加载；这是工程候选，非官方已验证保证。Container 可隔离适合容器的工具链，未必能代表桌面 IDE、GUI、OS Hook 或真实登录现场。不要为了统一环境牺牲真实测试条件。

Provider-neutral 应限于目标、权限、证据和交接契约。具体安装、规则发现与隔离方式应是短小的宿主说明；不把特定参数写进通用核心，也不以“中立”为由拒绝可执行的配置。

## 5. 三个问题的共同点与不同点

#43、#44、#32 共同暴露的是：正确文字没有自动转化为可靠行为。它们可能受到共享的复杂度、反馈不足或上下文问题影响；目前不能认定同一个根因。

- #43 的直接观察是错误交接；优先比较负责人默认与 placement pointer。
- #44 的直接观察是知识未被继承或行为未被保护；优先修工程反馈与接口证据。
- #32 的直接观察是额外步骤、等待及返工；优先测完整交付成本，而不是子代理数量。

保留独立失败案例和各自验收，合并一次“减法是否有效”的实验决策。不要合并成万能 memory/reliability 项目，也不要让每张 Issue 分别往启动协议增加一个 gate。

反馈循环的风险已经足够明显：规则增多后仍失效，继续用更强措辞和更多检查解释。尚不能证明这是所有失败的主因。跳出方式是允许删除、设置对照、用实际产物评分，并允许“候选规则无收益，所以不发布”。

## 6. 实施前只值得做的三个实验

以下均为未执行的实验建议。优先复用有可信原始轨迹的真实任务，不重演昂贵历史工程。

### 实验一：当前体系与最小契约的配对比较（优先）

选三个已知结果的任务：一个小修复、一个 Browser 已有产品推理的澄清任务、一个需要本地测试的实现任务。比较完整 v0.15 与上述单负责人最小契约；Matt lock、权限、安全边界与任务输入保持一致。首轮每类每臂两次 fresh session，共 12 次短运行，仅用于发现大差异，不宣称统计确定性。

保持共同 host/config/可见模型设置，在短时间内交错运行，随机顺序，避免后一臂看到前一臂产物。把已有产品推理提供给同等起点，不能通过多给某一臂关键资料制造胜利。

运行前固定判据：验收缺陷、越权、遗漏已接受要求、人类主动介入、返工、总完成时间与可得的费用。只数交接或回复长度会奖励错误的捷径。审核产物时尽量隐藏实验臂标记。

选择规则：若最小契约质量不差且协调成本明显下降，才试删相应机制；若多一次 Browser 检查稳定发现高价值独有缺陷，就保留该触发场景。单次严重越权要调查，不能用平均提速抵消。样本无区分度就承认不足，不无限追加直到得到 PASS。

### 实验二：global rules 的受控影响（按实际关切做）

第一轮同一 host、相同模型/产品版本和 repo SHA，仅改变一个已知全局输入，比“两台不同机器各跑一次”更能识别因果。用专用测试账户/已验证隔离 profile：最小配置、只含风格偏好、含额外规划/确认要求。每臂相同 Mission，至少重复几次，检查结果与成本，而非是否复述了规则。

若只有 workspace 规则可控，诚实称为“共同 global 基线上的增量实验”，不能冒充无 global 对照。优先利用实际加载清单/诊断；无害 marker 可作辅助，未输出 marker 不证明没有加载。

只有发现值得解释的影响，才在第二台 host 上交叉重复配置条件，检验可迁移性。直接做 Mac A/PC B 同任务会混入 OS、工具链、安装版本等变量，不能把差异全部归因于 global rules。

### 实验三：#44 的自然保护是否足够

在相应目标项目的隔离测试副本里，为 EOF 行为建立红绿可验证的集成测试；为 Hook 保留去敏接口 fixture 与最小现场 probe 指针。fresh Agent 不给旧聊天，完成一次相关重构/设计任务。

比较普通项目环境与加入通用 learning check 的环境：是否都能发现或阻止错误、是否额外增加仪式。若自然工程保护已足够，关闭“需要通用 Workflow gate”的假设。此处只提出实验，不授权或实施目标项目修改。

## 7. 减法清单

| 机制 | 未来版本建议 | 理由 |
| --- | --- | --- |
| Mission Contract / Run-to-Gate | 保留，压到任务实际需要的输入 | 是跨端价值最集中的部分 |
| 固定 SHA、诚实证据、关键授权、写隔离与汇聚 | 保留；可机械验证部分交工具 | 能直接防止审错对象、越界和集成竞态 |
| 每次需要时做完整 placement 四因素判断 | 改为负责人默认延续、换端例外判断 | 少做重复的宿主选择 |
| 每次中继必须给 Fresh/Continue 与理由 | 仅在会话选择真实影响任务时要求 | Browser 未必观察得到 IDE 健康度 |
| Browser 必须管理两端健康、复制有序五步上下文策略 | 交各端 Harness/当前负责人，核心只留交接输入要求 | 避免遥控不可观测状态和重复 Matt 流程 |
| Browser + IDE 固定双 Review | 改为风险和独立证据触发 | 正交目标不必固定为两个宿主门禁 |
| 上游漂移在普通启动中反复检查 | 移到升级维护任务或已有监控 | 锁定不变时，上游前进通常不改变当前交付 |
| 新 MAT_REF 只能取正式 release | 未来允许显式批准、固定 SHA 的例外 | 版本稳定需要 pin，release 标签不独自证明兼容性 |
| Matt 全套关系透镜 | 针对改变的调用/产物/依赖契约使用 | 不为每次升级填十维矩阵；不自动放宽现行锁定 |
| 测试候选先发布 immutable prerelease | 测试固定快照、生产正式发布分离 | 缩短验证内环，保留可追溯性 |
| 600-Line Soft Guard | 从跨端核心删除或退到维护建议 | 与跨端契约关系弱，不能替代结构与加载诊断 |
| “不得成为第四权威”等重复声明 | 删除重复，保留清晰来源/权限说明 | 防御性元规则不应成为常驻负担 |
| #44 通用 learning gate、global 分类机制 | 暂不新增 | 先验证自然工程机制与既有 probe |
| 行为 regression scenarios | 保留小而有区分度的集合 | 衡量真实行为；淘汰只测答案措辞的用例 |

固定 SHA 依赖锁值得保留，禁止自动升级也值得保留。挑战的是“只有上游正式 release 才能受控采用”和每次会话重复治理成本，不是鼓励浮动 main。当前 MAT_REF 与历史 tag 完全保持原义。

若只保留最有价值的一小部分，我会保留：一个负责人、清楚授权的任务与验收、项目内可执行反馈、可追溯产物与证据、真实阻塞/重大取舍时升级。其余机制按它发现的独有失败来证明价值。

## 8. 我会批准的下一步

只批准一次有成本上限的减法比较，先做实验一；实验二在 global 因素确实影响结论时加入，实验三由目标项目有真实相关工作时顺带验证。现有 #32 可承接比较，不为了全球规则再建一套治理项目，不重开 #14，不冻结 v0.16 方案。

先记录一个页内可读的最小契约候选和判据，再运行受控小样本。没有质量或成本收益就不改生产；有清楚证据时，仅修改对应机制，而不是全面重写体系。既有权限和正式发布边界继续有效。

## 9. 置信度与未知

高置信度：global 覆盖不等于隔离；pin 不等于完整环境可复现；固定 SHA 不证明本地执行；EOF 类事实优先由真实行为测试保护；当前试验协议承担了可识别的发布成本。

中等置信度：一个负责人、Browser 按需参与、风险驱动 Review 能降低本项目协调成本；现有强制义务确实可能抵消效率原则。需要上述对照才能判断收益大小。

低置信度/未核实：global rules 是否造成了 #32/#43/#44 的具体失败；当前 prompt 长度的因果贡献；最优 Browser 参与比例；Antigravity 的完整 native profile 隔离能力；两起工程案例的完整运行时契约；任何候选方案的长期收益。
