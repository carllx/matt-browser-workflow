# 测试体系独立审查：缩小承诺，先验证判题能力

日期：2026-09-27。状态：非规范性研究建议；未批准的评测与工具候选。

## 决策摘要

选择路线 C：**减少需要长期保证的 Workflow 行为，用少量确定性检查保护制品和硬边界，用窄模型实验回答具体决策，仅在产品集成风险发生变化时做真实 smoke。** 不建设完备平台，也不退回完全依赖感觉。

原定 Full v0.15 vs Minimal 实验：**REDESIGN FIRST**。撤回“先跑 12 次短实验”作为默认下一步的建议。先确认观测对象、可执行判据与宿主代表性；若实验只比较两份 prompt 的回答，不能用结果决定真实 Browser/IDE 组织架构。

只批准一个后续工作单元的话，我会批准：用现有制品和两组正反例验证一个最小自动检查闭环，先证明它会拒绝错误证据、不会把未运行记为 PASS。无需模型调用、平台、生产部署或用户操作多个 Session。

## 1. 真正的测试问题

需要回答的是：**哪种错误值得在交付前发现，什么证据足以发现它，以及发现成本是否低于它能避免的损失。**

当前“测试”混合了四个不同目标：

| 目标 | 能回答的问题 | 不能顺带声称 |
| --- | --- | --- |
| 制品与发布核验 | 文件、版本、引用、部署包是否正确 | Agent 会遵守其中规则 |
| 回归筛查 | 已知重要失败是否再次出现 | 所有历史能力都未退化 |
| 因果实验 | 候选机制相对基线是否带来收益 | 一次通过就长期可靠 |
| 真实使用观察 | 产品组合在实际任务中怎样表现 | 无控制条件也能归因到某条规则 |

同一个工具可以服务多个目标，但结果不能互相冒名。测试体系的价值是减少错误决策，而不是产生更多 PASS。

可确定检查的主要是有限制品和已记录动作；模型是否下一次仍做对，只能概率性评估。产品价值、合理架构、必要的提问、最佳推理宿主等不宜全部变成通用二值门禁。

授权、凭据隔离、不可逆操作、正式发布身份应尽量由工具/执行系统约束。行为 eval 检查 Agent 是否试图越界和是否正确处理拒绝；即使通过，也不能取代强制边界。

## 2. 当前机制的主要问题

### 2.1 有测试设计，没有自动 regression harness

[behavioral-regression-evals.md](../evals/behavioral-regression-evals.md) 是手工回归评测协议、基准场景和历史结果索引。称为 manual regression suite 合理；称为自动回归测试体系则不准确。

缺少的不是文件后缀，而是固定入口、实际被测输入、执行与采证、可检查的判题逻辑、失败退出和结果比较。每轮靠 Agent 临时理解 Markdown、组织执行并宣判，会让运行方式与判据一起漂移。

### 2.2 测试有时保护流程表述，而非用户结果

R5 明确把 Fresh/Continue 文本及理由作为每次 Work Order 的必要输出。这会奖励满足格式，即使用户没有因此得到更好交接。R1 的“显式标记并行候选”也只是计划信号；现行文档已经要求真实执行证据，不能把这些要求降回关键词匹配。

R6/R7 刻意按决策评分，优于只检查复述。然而短输入已直接给出关键事实，测试的是应用已给事实，不是长历史里找回事实。不能据此证明实际检索或跨阶段连续性得到修复。

### 2.3 Fresh Session 不是完整隔离

ChatGPT 官方说明 Project 内聊天可以引用同 Project 的其他对话，project-only memory 也保留这一能力。因此现行“每个场景 Fresh Browser Session”的做法，单独不能证明场景互不污染。[Projects 文档](https://help.openai.com/en/articles/10169521-projects-in-chatgpt)

这也修正前次报告对 fresh-session 配对试验的默认设想。需要验证实际记忆设置与隔离方式；若不能控制，应将真实 Project smoke 视为部署抽查，不将其包装为干净 A/B。不要为了隔离而反过来让用户手工建大量 Projects。

### 2.4 H/S/T 解决了真实发布约束，但不是理想实验边界

[#35](https://github.com/carllx/matt-browser-workflow/issues/35) 的历史清楚：candidate 无法通过已发布身份要求，先提出 tag，再因同一要求升级成 published prerelease。这不是不可变性天然要求三层坐标，而是实验被生产启动规则约束后产生的适配。

未来宜由外部测试调用明确指定“测试对象及固定快照”，候选文本是被测输入，不能同时成为批准自身能否测试的裁决者。普通实验记录 commit、实际输入摘要、配置与判题版本即可；需要长期重放时还应保存对应非敏感输入/输出，SHA 本身不保证内容永远可取。

生产发布保持正式身份和不可变 tag。H/S/T 历史证据保留；当前协议未获修改前不得静默绕过正式 smoke 门禁。隔离的离线研究可先开展，但不记作现行正式 runtime gate PASS。

还有一个小而真实的限制：identity overlay 是模型可见文本，“只有元数据 diff”不能严格证明行为完全不受影响。通常影响可能很小，但可追溯性不是语义等价证明。

### 2.5 “这次通过”与“可靠/更好”被放在同一个 PASS 下

[Scope probe](../evals/scope-fidelity-probe-2026-09-11.md) 的基线/候选均通过，不证明收益，也不说明该场景完全没用：它仍可能防守回归。[Strategy probe](../evals/bounded-strategy-adjudication-2026-09-11.md) 的带反馈修订适合开发调试，不能充当独立确认。

[#33 smoke](https://github.com/carllx/matt-browser-workflow/issues/33#issuecomment-5496575648) 是存在的历史执行报告，但其中模拟 IDE evidence 和替换 fixture 限制了可得结论。本次没有完整原始工具轨迹，不能重新审计端到端并发、人工分钟或长期效率。

不要挑成功重跑覆盖失败。网络错误、工具拒绝、样本无效、行为失败与未覆盖需分别记录。一个 smoke 可以发现故障，不足以估计低失败率；不能用单次 PASS 作全面回归证明。

## 3. IDE 自动检查究竟证明什么

| 检查 | 类型及可证明范围 | 常见遗漏 |
| --- | --- | --- |
| `git diff --check` | 确定检查已覆盖 diff 的空白错误/冲突标记 | 不检查行为；未指定正确范围时可能漏 staged、untracked 或提交差量 |
| Git SHA、tree、diff 路径 | 固定对象及明确路径约束可确定核验 | 短 SHA、移动 branch、submodule、dirty/untracked 状态；路径合法不等于语义没越界 |
| 三文件版本、lock 值、ref | 格式/一致性是确定检查；远端解析是当时观察 | 可解析不等于正式 release，不等于实际加载了该版本 |
| 本地链接、Markdown 结构 | 路径、锚点与可解析结构可自动检查 | 页面可访问不等于内容支持结论；需选择正确 Markdown 解析规则 |
| Secret pattern scan | 某检测器未发现其能识别的模式 | 非“没有任何秘密”的证明；未覆盖编码、日志、历史等不能暗示覆盖 |
| 文件长度/字节数 | 数值可确定测量 | 无法证明可维护性、token 数或实际加载完整性 |
| 重复规则检查 | 完全相同片段可机械发现 | 语义重复、冲突、无意义义务仍需判断，不属于纯 L0 |
| 符合 Matt、无过度设计、无遗漏 | Agent-judged review | 能发现问题，但不是独立行为证据或客观 oracle |
| 日志显示工具调用 | 此次请求/返回可核实 | 调用了不等于成功；成功不等于结果正确或对应最终候选 |
| Agent/CLI exit 0 | 进程或协议层成功状态 | 不等于任务验收完成 |
| 本地/API 评测 PASS | 所测 harness/model/input 下的结果 | ChatGPT Project 加载、记忆、GUI 和真实 relay friction 仍未核实 |

同一个 Agent 修改后审读有价值，类似开发者自查，但不能提供独立性。换子代理可减少部分同上下文偏差，却仍可能共享模型偏差、泄漏的答案或相同错误判据。最强增量常来自外部可检验结果，而不是再增加一位 reviewer。

无法诚实给出“能自动化 80%”这样的比例：没有统一分母和人工时间账本。制品检查可以无人值守；行为实验的运行/采证可以自动化；解释与宿主代表性只能部分自动化；原生产品 smoke 的零人工尚未验证。

## 4. 最重要的遗漏检查

1. **实际测了什么**：保存真正发送的 instructions/context 或其可恢复快照、候选 SHA、fixture、可见模型标识、宿主与判题器版本。不能只记录目标文件 SHA，却不知运行时加载的内容；不可观察的产品内部输入明确 unknown。
2. **确实运行并得到终态**：样本数大于零、每个预期样本有终态、未被缓存冒充新运行、未超时丢输出、未因权限/认证/网络失败跳过。工具错误不应落成普通 PASS 或混入行为失败率。
3. **产物与证据绑定**：最终文件状态、测试命令及各 exit code、reviewed/tested candidate 对应关系。一个旧日志、别的分支通过或仅模型说通过都不充分。
4. **检查器真的会失败**：注入 stale SHA、缺失测试事件、工具拒绝、异常退出却声称成功等反例；也提供允许的合法变体，防止检查器过严。
5. **独立状态和数据泄漏**：案例之间的文件、进程、外部资源、对话/Project memory；不给被测 Agent 判题答案或上一臂批评。模拟工具返回需与当前动作一致。

具体官方反例：Antigravity headless 的工具若需要无法获得的审批，会 soft-deny，但运行可以继续并 exit 0。其 JSON/stream-json 能帮助采证，不能只检查 shell exit code。[Headless 文档](https://antigravity.google/docs/cli/headless/)

少量静态检查也要区分候选与发布阶段：开发中的目标 WORKFLOW_REF 不存在，可能完全正常；正式发布/部署才要求实际 release 存在且内容对齐。把发布条件机械搬到每 commit L0 会重建 H/S/T 循环。远端超时应报告核验不可用，而非断言 ref 不合法。

## 5. 推荐架构：按要证明的结论选择检查

不采用“每层都要建齐”的金字塔。只保留三种可按需组合的活动：

### A. 廉价制品检查

可在变更时自动跑：选定文件/版本/锁定值、相对链接和内容包一致性、diff 范围与已知秘密模式。发布时才读取 release metadata、peel tag、核对部署包。

不在 L0 伪装实现“没有过度设计”“所有规则无语义重复”。仓库很小，无需专门 schema 系统或 Markdown 语义编译器。解析少数稳定字段和必要文件结构即可。

### B. 围绕真实失败的契约案例

一个案例应包含决策前输入、允许动作、必要环境/工具返回、可检验终态和少量顺序约束。先从最有价值的错误开始：失败前置仍推进、旧 SHA 冒充当前证据、越出明确范围、漏执行却声称完成。

对文件与真实工具行为，用隔离 test repo 和可控失败注入；对单一决策，用短模型输入。两者都只证明其覆盖范围。API/CLI 替代环境不命名为 Full ChatGPT Project。

判题优先顺序：终态/事件的可执行断言 → 正反例校验判题器 → 有边界的差分/变形案例 → 少量盲化模型判断。只在结果将改变决策且仍有争议时升级人工，不要求用户逐例标注。

### C. 原生产品部署抽查与真实失败采样

检查只有实际产品能暴露的问题：Sources/Instructions 部署路径、记忆影响、工具可用性、真实交接可完成性。不是把所有案例再人工执行一遍。

日常实际使用只在出现失败或重大纠偏时保留去敏的最小输入、动作、产物与版本线索。不要全量录屏/存聊天、建 telemetry 服务；runner 自身产生的记录自动留存即可。

### 对 L0–L3 提案的裁决

| 候选 | 裁决 |
| --- | --- |
| 每 commit L0 | 保留廉价、本地、确定部分；远端发布检查移到适当事件；语义判断不归 L0 |
| impacted L1 | 只在能回答当前决策、有校准判据时运行，不强制每处 prompt 调整都付费评测 |
| L2 integration | 为需要真实动作的少数失败使用；它是特定 harness 集成，不是 Browser Project 模拟等价物 |
| 每 RC full core + 一次 L3 | 不作为通用义务；按变更风险、已知产品漂移和现有证据决定 |

模型行为概率性不妨碍测试，但妨碍“每次跑绿就是保证”的理解。关键约束的确定性违规足以阻止该候选；模糊质量评分不宜单次作为硬阻塞。

## 6. 真正值得采用的其它方法

**首选：contract testing + 最小真实失败 fixture。** 验收是一个可观察动作或终态，不是固定整条优秀轨迹。

**第二：负例与 mutation 检查判题器。** 删除一次必需成功事件、替换错误 SHA，验证会失败。prompt 删除一条规则后仍 PASS 则可能说明模型已原生具备行为，不能一律要求 prompt mutant 必须失败。

**第三：少量 differential / metamorphic checks。** 相同输入比较基线/候选，但基线不是正确答案。加入“只是改名/无关背景”时结果应保持；把前置成功改成失败，推进决定应变化。变换必须保持或明确改变真正语义，不能随意重排有时序含义的事实。

**第四：已有记录重评与有限重放。** 历史输出重评分验证 grader；新候选重新执行历史输入验证候选；固定工具返回模拟验证局部决策。三者不同。新策略请求了录制轨迹之外的工具/状态时应判超出 replay 范围或进入受控环境，不能喂不相关旧响应。历史读取轨迹不能证明新的副作用真的安全。

暂不建设通用 property generator、多模型排行榜、模型投票委员会、全自动失败提炼器。可以让 Agent 辅助提取去敏 fixture，但“当时究竟知道什么”和预期结果仍需审核；不得泄漏事后答案。安全可逆任务上的小范围试用可补证，不能让 canary/shadow 在生产中重复产生副作用。

## 7. R1–R7 与 sentinel 的处置

| 场景 | 建议未来处置 |
| --- | --- |
| R1 独立工作与汇聚 | 保留有限集成案例；检查必要结果齐全、无竞态、合理汇聚。并行数量/显式措辞不做普遍硬门禁 |
| R2 小任务停止 | 保留明确范围与产物断言；额外步骤/耗时作诊断，不能仅按字数或工具次数判失败 |
| R3 真依赖 | 保留失败前置、不许改变现场等动作约束，是最值得保护的部分 |
| R4 自治/人工成本 | 合并到一次真实闭环案例；自动记录阻塞请求与进度消息之别，必要性仍需判断 |
| R5 Session Targeting | 建议取消固定格式义务后退役对应格式测试；保留不凭空声称会话存在、关键输入能传递的结果要求 |
| R6 范围保真 | 保留少量反例与合法授权变化，按决定/产物评分；不能称为长历史检索测试 |
| R7 前瞻 | 归为选定设计案例，暂不作为所有 release 必跑门禁；部分前置保护可与 R3/R6 合并 |

Sentinel 可以作为廉价报警器，但不是覆盖证明。优先覆盖不同失效机制，不追求一个整齐固定数量；不只挑模型最容易通过的模板。

旧案例退役条件：对应义务被明确删除、被更强/更便宜案例覆盖、宿主不再使用、或无法给出可信判据且收益不足。长期 PASS 本身不构成退役理由；饱和案例仍可能保护重要回归。保留原案例和退役原因，退出活跃运行集合，不抹去历史。

简单 change-impact selection 足够：本地文档/非加载研究改动仅制品检查；特定契约变动跑相关案例；启动/授权/上下文/全局角色变化才扩大到小型核心集。Prompt 有非局部影响，不能靠文件路径映射保证“其余不受影响”；重要横切变更扩大检查，不建依赖图平台。

目前 R5 等仍是已发布义务，这里提出的是未来删除建议，不因此把当前违反规则判作合规。

Promptfoo tracing 需要 provider 接入并传播 trace context，不会自动看见任意封闭宿主内部行为。[Tracing](https://www.promptfoo.dev/docs/tracing/)。响应缓存可节省判题调试成本，但重复命中缓存不算新的独立行为样本。

官方 ChatGPT Projects 文档提到 Compliance API 的项目资料/治理能力；本次没有找到能完整执行“创建/重置测试 Project、装载指定内容、驱动聊天并导出完整运行轨迹”的公开评测接口。不能把 API Platform Projects 或 Agents API 当作 ChatGPT Projects。

UI automation 可能帮忙上传、输入和截图，但选择器、登录态、长任务等待、导出及 memory 控制仍需实测。此时维护 UI robot 很可能比偶发 smoke 更贵；不作为当前默认方案。没有可靠接口时应明确保留产品验证空白，而不是伪造等价性。

## 9. Product smoke 何时跑、怎样减少用户负担

建议未来按事件运行：首次采用新部署方式；改动 Instructions/Sources 组织或启动/检索；改变真正依赖产品的工具/权限/记忆；已观察到产品行为漂移；发布包含上述实质变化。纯研究更新、普通链接/拼写修正，不值得重新做人机跨端实验。

合并相关变更后，一次有界的原生部署抽查可检查：正确候选来源、能读取关键输入、一次实际交接及验收、一个不会产生危险副作用的拒绝/失败分支。可在同一场景连续验证有关步骤；“fresh per fixture”仅用于独立决策问题，连续性测试反而必须保留多轮状态。

“一次 smoke”指一个检查工作单元，不是一个成功回答足以证明统计可靠性。实际 UI 如无机器可验证的内容导出，只能报告可见部署证据及读取行为，不能依赖模型自述宣称内部加载顺序和全文 hash 已验证。

不要求每个 RC 都重跑；未触及产品组合且已有适用证据时可以更少。但产品可能在 repo 不变时漂移，release cadence 也不能覆盖此风险。通过真实使用中的失败信号和已知产品变更触发抽查，不增设常驻监控工程；长期不用且要执行高后果任务时，再做一次必要预检。

用户“开始一次授权、结束一次看结果”应是自动实验设计目标：隔离环境准备、运行、采证、判题、汇总由 runner 完成；凭据在本地/CI 私有环境注入，日志去敏。事前明确可用权限、时间/费用上限和停止条件，不能用全权限跳过来伪造零打断。

有真实新决策或 human-only Skill gate 时，不能让 runner 伪造人类调用；提前由用户合法触发、选择不依赖这类触发的案例，或把该点标为未覆盖。合成 user simulator 可测对已给授权事件的反应，不能证明真实用户已经授权，也不能测真实人的思考时间。

若目标产品没有可用自动入口，需要一次集中人工部署/登录操作可能无法消除。不能据此让用户承担 12 个 Session 的实验操作；宁可减少频次和保证范围。离线模型的“提问次数”只是注意力代理指标，真实人工分钟在未测量时保持 unknown。

## 10. 原定 v0.15 vs Minimal：REDESIGN FIRST

我仍认为比较值得保留，但不再建议立即按三类任务、每臂两次执行。那是运行次数安排，尚不是有效识别策略。

需要先区分两个问题：

- **内容消融**：同一 harness、工具与输入，仅改变追加工作流文本。能说明这个替代环境中 prompt 差异的影响，不能证明 Browser/IDE 架构收益。
- **整套工作方式比较**：真实单负责人方式与双端方式。它本来就改变角色、可用上下文、交接等多项变量；可比较整体交付效果，却不能把改善归因于某一条规则。实际人工成本不能由模拟用户自动获得。

先做最窄的内容消融可作为排错筛查，命名为“替代 harness 下的 v0.15 文本 vs 最小文本”。不要用 v0.15 旧格式义务判最小方案失败；两臂共用用户结果、授权与证据标准。

先确认各臂实际加载差异，没有主控 v0.15/全局技能把最小臂重新污染。随机/交错运行，保留首次失败，模型配置尽量一致。只在初步信号有区分度时安排少量原生观察；不立即建立双 Agent 全仿真。

若可信差异只能靠昂贵人工重演才能获得，而所讨论的是低价值 ceremony，就 DEFER/DROP 实验，转为未来显式缩小承诺的决策；不是继续扩建测试平台。授权、安全等高后果约束不能仅因难测就删除，应迁到执行层或限制产品能力。

## 11. 最值得先自动化的项目与停止规则

按收益顺序：

1. **一个本地制品检查入口**：候选 diff、版本/lock、必要路径/链接、实际检查范围；以后再接 CI。发布字段检查按阶段区分，不全量在线查询每个 commit。
2. **结果完整性与候选绑定检查**：零样本、缺失终态、旧 SHA、拒绝工具仍称成功、部分失败被最后一个 exit 0 掩盖等。
3. **检查器的正反例测试**：确定正确记录可过、已知错误必拒绝；先验证判题器，再花钱生成更多样本。
4. **已有 CLI/API 的薄运行与采证驱动**：仅当选定行为需要模型运行时增加，复用官方 JSONL 或 Promptfoo，不先写 scheduler。
5. **少量版本差分汇总**：列出新失败、改善、未覆盖、无效样本和可观测成本；不做虚构总分。

这些不是要求全部立即实现。一个 100 行级脚本或现成工具配置可能足够，但行数不是预算保证；跨宿主真隔离和通用 UI 自动化显然不能用这个估计承诺。

简单停止规则：**若实验不能改变一个明确的保留/删除/发布决定，或在约定预算内无法取得能区分候选的证据，就停止追加实验。** 记录“不足以判断”，优先维持现状或提出删减低价值义务；不反复加样本直到 PASS。

测试成本应进入 feature 取舍，包括建设、误报处理、模型/API运行、发布操作和用户注意力。不能把“可靠性收益”和“小时”直接当可精确相减的数值，不建 ROI 分数表；回答“避免哪种实际损失、便宜替代是否足够、预算内结果会改变什么”即可。

建议退役或降级的高成本义务：每次中继固定会话指示、所有变更固定双 Review、每个候选 H/S/T 发布、通用效率/最优前瞻保证、每次更新全量真实 Browser 回归。它们未来是否删除需单独接受；本研究不修改现行规范。

## 12. 只批准一个后续工作单元

**名称：最小自动检查闭环可行性验证。** 建议最多一个工作日，作为未来成本上限候选，不是本次开始实施。

输入为当前固定 repo snapshot，外加两组可明确标注 synthetic 的证据记录：候选/测试证据匹配与不匹配；已完成验收与工具拒绝/缺失事件却声称完成。只检查其实际可判性质，不伪装真实 Agent trace。

交付一个命令、少量 fixture 和简短结果：制品基础检查完成；正确记录通过；所有预置错误被识别；缺数据返回未核实/错误而非 PASS；无模型 API、无浏览器操作、无生产写入。已有原始记录可替代 synthetic，只有摘要时不补造轨迹。

这个工作单元证明自动判题和证据绑定值得继续，不证明 Workflow 改善。若顺利且存在明确待决问题，再单独给薄 runner 加一个有代表性的模型案例；若连可靠判据都难以建立，停止自动化并重新判断该行为是否值得承诺。

## 置信度与未知

高置信度：仓库尚无可重复执行 runner；手工协议不能自动提供回归保障；Fresh Session 不保证 Project memory 隔离；可执行 oracle 与实际终态比自报 PASS 更强；CLI exit 0 存在明确反例；OpenAI Evals 新集成面临已公告退役。

中等置信度：少量契约案例、负例校准、按风险选择产品 smoke 比现行全流程更经济。它是基于项目规模与证据的工程判断，尚无本项目成本对照。

未知：本地 CLI 是否已安装且可用、账户支持的模型/API、ChatGPT Project 实际记忆设置与可观测性、GUI 自动化稳定性、当前所有 eval 的真实人工耗时、最小方案的长期质量。本次没有将厂商能力描述等同本机运行验证。

`research` 已实际执行：后台生态研究、一手资料核查、单一仓库研究报告。没有执行产品行为测试，不声称 R1–R7 或新候选 PASS。只新增本报告；正式规则、MAT_REF、历史 release 与生产 Project 保持原样。
